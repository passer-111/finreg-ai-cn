# finreg-ai-cn

**中国金融领域 AI 合规政策知识库** —— 机器可读、带时效性治理、可溯源。

检索当前有效的 AI 合规政策，聚焦银行业、证券期货业、保险业与支付清算领域。
每条记录都标注**此刻是否有效**、**被谁取代**、**最近何时核验过**。

## 这个项目解决什么问题

中国金融领域的 AI 合规要求散落在多个监管机构的数百份文件中：
人民银行、金融监管总局、证监会、网信办、工信部，以及各类行业自律组织。
对一家中小金融机构而言，真正的困难不是「找不到文件」，而是三个更具体的问题：

1. **这份文件现在还有效吗？** —— 政策常被修订、取代、废止，但绝大多数
   资料库只保留最新版，不记录版本链。
2. **它到底要求我做什么？** —— 原始文件动辄三四十条，其中真正产生义务的
   可能只有十几条，需要逐条提炼。
3. **我凭什么相信这条记录是对的？** —— 没有核验时间戳与官方链接的
   「知识库」，本质上只是一个不可验证的传言集合。

本项目的目标就是把这三个问题变成可查询的数据。

## 时效性治理是怎么做的

这是本项目的核心机制，也是与「爬虫 + 全文检索」类方案的根本区别。

### 1. 状态是核验出来的，不是推断出来的

`status` 取十个受控值之一：`draft` / `consultation` / `published` /
`effective` / `partially_effective` / `amended` / `repealed` /
`superseded` / `expired` / `unknown`。

注意 `amended`（已修订，新版有效）与 `partially_effective`（部分有效）
**都算「当前有效」**——它们是「有效但需注意版本」，与「已废止」有本质区别。
这个区分在实务中经常被搞错。

### 2. 版本链而非快照

每条记录通过 `supersedes` / `superseded_by` / `amends` / `amended_by`
组成有向链，且**双向指针必须闭合**：声称被某文件取代，那个文件就必须在库中存在。
校验器会强制检查这一点。

为什么需要这个：合规审查经常要判断「**当时**适用的是哪一版，
**当时**的义务是什么」。只保留最新版的知识库无法回答这个问题。

### 3. 允许「不知道」，且要求显式承认

如果一条记录现行有效但施行日期无法确认，`effective_from` 应当留空，
并在 `verified_note` 中说明原因。这会产生一条**警告**（不阻断），
而不是**错误**（阻断）。

这个分级是刻意的：如果把「缺日期」判为错误，维护者会被迫编造一个日期
来让校验通过——**那才是对数据质量真正的伤害**。

#### 这条规则现在有机制执行了（2026-10-05 新增）

上面这条规则写了很久，但**没有任何机制执行它**。结果是 9 条记录里有 3 条
违反了它——字段填了具体日期，核验说明却承认该日期尚未确认。记录同时主张
「施行日期是 X」和「不知道是不是 X」，而下游只能看到那个日期，会把它当事实用。

现在由两条校验规则兜住：

| 规则 | 触发条件 | 级别 |
|---|---|---|
| **规则 11** | `effective_from` 非空，但 `verified_note` 承认该日期尚未确认 | **错误**（阻断） |
| **规则 12** | `verified_by=automated` 且 `effective_from` 非空，但说明未交代日期出处 | 警告 |

规则 11 判为错误而非警告，是因为它描述的不是「信息缺失」而是「信息自相矛盾」——
缺失是显式的空白（使用者会去问），矛盾却会静默地变成一条假事实。

判定方式是**句内绑定**：只有当「生效日期」这个话题与「不确定」这种表态出现在
**同一句话**里才算矛盾。否则一条说明里讲配套细则「尚未明确」也会被误报。
规则 12 只约束自动整理的记录，因为「把字段填满」是自动化产出的结构性倾向，
而人工核验过的记录，核验行为本身就是依据。

**必须说清这条机制的局限**：它是**启发式护栏，不是证明**。它能拦住
「承认了却仍填值」这一种形态，拦不住「悄悄编一个日期且全文不提任何不确定」——
后者与诚实填写的记录在字面上无法区分，只能靠人工核对原文。
这也正是 `last_verified` 台账与 `verified_by` 字段存在的理由。

### 4. 陈旧记录自动浮出

`last_verified` 记录最近一次核验日期。超过 180 天未核验的记录会：

- 在 `finreg validate` 中列出
- 进入 `finreg stale` 的待办清单
- 进入变更流，提示需要人工复核

配套的 GitHub Actions 工作流每日自动检查。

## 快速开始

```bash
# 安装（含开发依赖）
pip install -e ".[dev]"

# 看看现在有效的政策有哪些
finreg list --effective-only

# 查看某条记录的完整信息（含逐条义务）
finreg show nfra-2026-ai-guidance

# 执行抓取，发现新政策（不写盘）
finreg fetch --dry-run

# 校验仓库数据完整性
finreg validate

# 列出超期未核验的记录（时效性治理的核心工具）
finreg stale

# 预演：看看再过一个月，哪些记录会进入待核验队列
finreg stale --days 30 --as-of 2027-01-01
```

不需要克隆仓库也可以直接用数据：所有记录都是普通 YAML 文件，
在 `data/policies/` 目录下。

### 全部命令

| 命令 | 作用 |
|---|---|
| `finreg list` | 列出政策记录，支持按状态 / 机构 / AI 相关度 / 主题筛选，`--json` 可机读 |
| `finreg show <id>` | 查看单条记录的完整信息，含逐条关键义务与条号 |
| `finreg stale` | 列出超期未核验的记录。`--days N` 设阈值（默认 180），`--as-of YYYY-MM-DD` 指定基准日 |
| `finreg fetch` | 执行抓取流水线，发现新政策并产出变更流。`--dry-run` 只报告不写盘，`--show-dropped` 列出被关键词过滤丢弃的条目，`--force` 允许运行未启用的源（`--source` 指定） |
| `finreg validate` | 校验全部数据的完整性（CI 门禁） |
| `finreg validate-sources` | 只校验数据源登记表 `data/sources.yaml` |

#### `stale --as-of` 为什么存在

判定「某条记录是否超期未核验」必须有一个基准日。默认取北京时间今天，
但把它做成可传入的，是为了两件事：

1. **预演**。想知道「再过 60 天哪些记录会进入待核验队列」，直接传未来日期即可，
   不必等到那天。
2. **测试不随时间漂移**。若测试隐含地以「今天」为基准，那么只要核验台账
   不天天更新，天数就会逐日增长，断言迟早失效——而代码一行没改。
   这类「会自行变红的测试」比没有测试更糟：红过一次之后人们就开始
   习惯性忽略红灯，校验闸门随之失效。

```bash
# 今天的视角
$ finreg stale --days 30
没有超过 30 天未核验的记录。

# 快进到 2027-01-01 的视角（会显式回显基准日）
$ finreg stale --days 30 --as-of 2027-01-01
共 9 条记录超过 30 天未核验（基准日 2027-01-01）：

  cac-2022-algorithm-recommendation         90 天    状态=effective
    └─ https://www.cac.gov.cn/2022-01/04/c_1642894606364259.htm
  ...
```

### 输出示例

```
$ finreg list --effective-only

共 8 条记录：

  cac-2022-algorithm-recommendation      effective            2022-03-01  互联网信息服务算法推荐管理规定
  cac-2023-genai-interim-measures        effective            2023-08-15  生成式人工智能服务管理暂行办法
  nfra-2026-ai-guidance                  effective            2026-XX-XX  关于银行业保险业人工智能安全开发应用的指导意见

```

> 本项目宁可显示「日期待核验」，也不填一个未经证实的日期。

## 数据模型（字段字典）

一条记录的完整结构见 `schema/policy.schema.json`。核心字段说明如下。

### 身份

| 字段 | 说明 |
|---|---|
| `id` | 全局唯一标识，格式 `<机构代码>-<年份>-<语义化短名>` |
| `title` | 官方全称，必须与官方页面标题完全一致 |
| `issuer` | 发布机构全称；多部门联合发布时用顿号分隔 |
| `issuer_code` | 机构代码，须在 `data/sources.yaml` 的 `issuers` 中登记 |
| `doc_number` | 发文字号，如 `银发〔2023〕89号` |

### 效力（两个正交维度）

| 字段 | 取值 | 说明 |
|---|---|---|
| `instrument_type` | `法律` / `行政法规` / `部门规章` / `部门规范性文件` / `行业自律规则` / `国家标准` / `地方性文件` / `其他` | 这是什么级别的文件 |
| `bindingness` | `binding` / `soft-law` / `guidance` / `consultation` | 它是否产生强制义务 |
| `ai_relevance` | `core` / `related` / `background` | 与 AI 合规主题的相关度 |

**为什么要把这两个维度分开**：一份「指导意见」在文件层级上只是部门规范性文件，
但其正文中的「须」「不得」「严禁」对应实质义务，违反同样会招致监管措施。
只看文件层级会严重低估合规压力。

### 时效（核心）

| 字段 | 说明 |
|---|---|
| `status` | 法律状态，十个受控取值之一 |
| `published_on` | 官方发布日期（注意区别于成文日期，二者常不同） |
| `effective_from` | 施行日期；无法确认时留空并在 `verified_note` 说明 |
| `effective_until` | 失效日期；多数文件为 `null`，需主动核验 |
| `supersedes` / `superseded_by` | 取代关系，双向指针必须闭合 |
| `amends` / `amended_by` | 修订关系，同上 |
| `versions[]` | 版本历史，每条含独立的日期、状态与原文链接 |

### 溯源

| 字段 | 说明 |
|---|---|
| `source.url` | 官方页面链接，**必须**可公开访问 |
| `source.tier` | 来源等级，**必须**为 `primary` |
| `source.fetched_at` | 抓取时间（带 `+08:00` 时区） |
| `source.content_hash` | 正文 SHA-256 摘要，用于检测内容变更 |
| `last_verified` | 最近一次核验日期 |
| `verified_by` | `human`（人工逐项核对）或 `automated`（仅自动确认可访问） |
| `verified_note` | 核验过程说明；状态为 `unknown` 或核验遇阻时**必须**填写 |

### 内容

| 字段 | 说明 |
|---|---|
| `topics[]` | 主题标签，取自受控词表 |
| `applicable_to[]` | 适用主体清单 |
| `key_obligations[]` | 关键义务，每条含 `clause`（原文条款定位）与 `summary`（人工撰写的概括） |

### 第二种数据类型：执法记录（罚单）

政策文件回答「**应该怎么做**」，行政处罚记录回答「**没这么做会怎样**」。
两者的字段结构、来源形态、可信度判断方式都不同，因此是两个独立的
数据类型与两份独立的 schema，而不是把罚单塞进政策记录里凑合。

为什么罚单值得单列一类，而不是当作「另一种政策」：

| | `data/policies/` | `data/enforcement/` |
|---|---|---|
| 回答的问题 | 应该怎么做 | 没这么做会怎样 |
| 谁产生 | 机器发现 + **人工提炼义务** | 机器抄录 + **人工认定收录** |
| 可信度怎么判断 | 是否逐条对照过原文 | 字段是抄的还是核过的 |
| 更新节奏 | 低频（每年数十条） | 中频（人民银行一次公示可覆盖十几家机构） |

**它的核心用途是校验政策侧的义务清单。** 政策里的 `key_obligations`
是人工从原文提炼的，提炼得对不对无从验证；而罚单里「违反数据安全管理规定」
这样的表述，直接说明监管实际在查什么。两者对照才能回答三个问题：

1. **义务清单写全了吗？** 监管在处罚某类行为，而我们的义务清单里没有对应条目。
2. **写了的东西监管真的查吗？** 义务清单里写了，罚单里从没出现过同类违规。
3. **中小机构实际栽在哪？** 罚单的当事人类型与违规类型分布，是「客户痛点」
   最直接的证据，比任何访谈调研都硬。

因此 `related_policies` 是本类型**最重要的一个字段**——它把「违规事实」与
「对应义务」连起来。空着也能用（罚单本身仍可检索），但只有填了，
知识库才真正具备反向校验义务清单的能力。它的引用闭合由 `finreg validate`
机械校验：指向一条不存在的政策会直接报错。

一条与政策记录不同的纪律：**官方行政处罚公示不含「处罚依据」条款**
（实测人民银行公示表格只有违法行为类型、处罚内容、决定机关、决定日期等列）。
因此 `legal_basis` 默认就是空的，**这不是缺失而是事实**。
绝不从「违反数据安全管理规定」倒推出「违反了《数据安全法》第 X 条」——
那种倒推看起来很有价值，但它是一条没有出处的推断，一旦写进记录就会和
官方原文混在一起，使用者无法分辨哪条是抄的、哪条是猜的。

抓取侧已可用（`finreg fetch --source pbc-administrative-penalties --force`
实测一次从 20 份公示文书中还原出 63 条当事人记录），
但 `data/enforcement/` 目录当前为空——因为录入标准依赖尚未建立的
「判定规则层」，详见 [`data/enforcement/README.md`](data/enforcement/README.md)。

> 复核同时发现，网信办把不同类型的文件分列在三个互补的栏目下，
> 因此本次把它拆成三个源。其中「政策文件」栏目的
> 《金融产品网络营销管理办法》是「金融 × 互联网信息服务」的直接交叉依据，
> 属早期覆盖盲区。

> 为什么停用 `nfra-consultations` 而不是凑合着用：实测发现配置里的栏目 id
> 返回的是「交强险业务公告」「拟录用公务员公示」等无关文件，
> 与「征求意见稿」完全无关。如果保留这个配置，征求意见稿分类里会混入
> 大量无关公告，而且因为抓取状态是 `ok`，**没有任何机制会提示异常**。
> 这属于静默污染，比抓不到更危险。

> **`pbc-regulations` 保留 0 条不是故障。** 补上关键词丢弃计数后看到
> 「已剔除 5 条疑似栏目导航链接 / 已滤除 21 条未进入结果的关键词过滤丢弃」，
> 把 21 条逐条看了：全部是《中国人民银行公告〔2026〕第N号》、
> 跨境资金集中运营、境外贷款、房地产信贷、非银行支付机构分类评级等
> 与 AI 无关的文件。源是活的（正常解析出 21 条），只是最近这批确实没有
> AI 内容。**这正是补计数之前无法区分的一件事**：以前只看到 `条目数=0`，
> 分不清是「源坏了」还是「源头确实没有」。
>
> 附带发现一处清洗小缺口：列表页页脚的 `京ICP备05073439号` 因标题长度
> 超过导航链接判定阈值（12 字）而未被剔除，最终由关键词过滤挡下。
> 目前无害，但说明导航启发式对「较长的页脚文本」无能为力——
> 记录在此，待后续用更稳的结构定位方式解决。

## 自动化（GitHub Actions）

仓库自带两套工作流，各管一件事：

| 工作流 | 触发时机 | 做什么 |
| --- | --- | --- |
| `validate.yml` | 推送主干、每个 PR、手动 | 三个并行作业：代码质量（ruff + mypy）、跨 4 个 Python 版本跑测试、数据完整性校验 |
| `fetch.yml` | 每天北京时间 06:00、手动 | 抓取各监管机构官网，把新发现写入 `data/changes/` 并自动提交 |

依赖按 `requirements.txt` / `requirements-dev.txt` 中的**精确版本**安装，
而不是用 `pip install -e ".[dev]"`：`pyproject.toml` 里的约束是范围（`>=`），
上游一发新版就可能让 CI 因为与本项目无关的原因变红。

### 自动化的边界：它不碰 `data/policies/`

`fetch.yml` 只会写入并提交 `data/changes/`，**绝不会修改 `data/policies/`**。
这是刻意的，不是还没做：

- 抓取器负责**发现**，人负责**认定**
- 结构化记录里的每个字段值都必须由人从官方原文中读出来。
  让程序直接往里写记录，等于把「不可核验」引进了知识库的根子上——
  而「可核验」正是本项目区别于二手汇编的唯一理由
- 所以 `data/changes/` 里是**候选**，未经核验，不能作为合规依据

### 源失效会被追着问，不会悄悄过去

如果某个源本次返回 `failed` 或 `degraded`，工作流会：

1. 把该源连同错误详情写进 Actions 的**任务摘要**（打开流程页面即可见，不必翻日志）
2. 自动开一个 issue 跟踪；若已有未关闭的同类 issue，则改为追加评论——
   保留完整时间线，能看出问题是持续的还是偶发的，也避免每天开一个新的把列表刷满

`degraded` 同样会上报，而且更需要上报：它的含义是「抓取器跑通了，
但一条都没解析出来」。这正是站点改版的典型征兆——**看起来成功，实际是失明**。

### 三个运维注意点

**1. 首次启用请先手动触发一次。**
GitHub 的运行器在境外，部分中国政府网站可能存在境外访问缓慢甚至被拒绝的情况。
不要假设一切正常——若某个源稳定报 `failed`，应改为在境内机器上手动抓取，
而不是让它每天刷一条失败记录。手动触发时可以填 `source` 只抓单个源，
或勾选 `dry_run` 试跑而不写文件。

**2. 机器人提交不会触发 `validate.yml`。**
用内置 `GITHUB_TOKEN` 产生的推送**不会触发其他工作流**
（GitHub 为防止递归触发而如此设计）。
因此 `fetch.yml` 把 `finreg validate` 放在**提交之前**作为闸门——
否则机器人就拥有了一条绕过校验的提交通道。
同时这也意味着：不要随意删掉那个「校验数据完整性（提交前闸门）」步骤。

**3. 主干若开了分支保护。**
机器人会被拒绝推送，`fetch.yml` 的提交步骤会失败。
两种处理方式：把机器人加入允许直接推送的名单，
或者把 `fetch.yml` 改成提 PR 由人合并。
不建议为了迁就自动化而关闭分支保护。

### 为什么 mypy 只检查 `src`，不检查 `tests`

先说一段值得记的教训。**这里原本写的是「因为 `tests/` 下没有 `__init__.py`」，
并把范围缩到 `src` 当作解决方案——那是规避，不是修复。**

真正的问题是：`tests/test_fetchers_offline.py` 里写了
`from tests.conftest import ...`，**这行代码本身就在要求 `tests` 是一个包**。
不加 `__init__.py`，这个导入就只能靠「隐式命名空间包」侥幸成立，
而它能否解析取决于运行环境把哪个目录放进了 `sys.path`。

代价在 CI 上兑现了：**本地 Windows 能跑通，ubuntu-latest 上直接收集失败**，
pytest 报「中断：收集错误」并以退出码 2 结束；因为四个 Python 版本一视同仁
地挂，看起来像代码问题，实际是导入机制问题。

修法是补上 `tests/__init__.py`（原因与验证记录写在那个文件里）。
补上之后，「Source file found twice under different module names」这条
mypy 报错也随之消失——它本来就是同一个根因的另一副面孔。

**但范围暂时仍保持 `src`**，因为扩到 `tests` 会撞上另一堵与本项目无关的墙：
mypy 解析 tests 的导入链时会走进 site-packages，在 numpy 的 `.pyi` 里报
「Type statement is only supported in Python 3.12 and greater」——
那是第三方存根的问题，而本项目声明的 `python_version` 是 3.10。
为一个第三方存根放宽自己的检查尺度不值得。

所以结论是：**会被别人 import 的代码（`src`）有严格类型保证；
`tests` 由「真的把它跑起来」（pytest）加 ruff 两层覆盖。**
一个永远红的检查比没有检查更糟——它会让所有人习惯性地忽略红色。
若将来要把范围扩到 `tests`，先解决 numpy 存根那条，别直接改配置。

## 设计原则

下面每一条都对应一次具体的踩坑，不是空泛的口号。

### 单源失效不拖垮整体

每个抓取器都被独立隔离，任何异常都转成 `FetchResult(status="failed")`，
绝不会向上冒泡中断流水线。失败源会被记入报告与变更流，
**而不是静默消失**。

### 明确失败优于静默错误

这是本项目最重要的一条。

抓取器最危险的失败方式不是崩溃，而是「成功地」抓回一堆垃圾——
导航链接、统计数据、页脚备案号——同时流水线报告 `status=ok`。
使用者看到「今天没有新政策」，而真相是抓取坏了。

具体对策：

- **0 条报 `degraded` 而非 `empty`**：因为无法区分「确实没有新政策」
  与「选择器失效了」
- **结果质量自检**：标题平均长度过短说明抓到的是导航链接；
  日期命中率过低说明字段映射已失效
- **站点自检**：政府网站改版后旧 URL 常被重定向到首页而非返回 404，
  此时应主动失败而不是「成功」抓到首页导航

### 清洗操作必须可见

剔除任何条目都要让数量出现在报告里：

```
[OK]     pbc-regulations          条目数=0
         ├─ 已剔除 5 条疑似栏目导航链接
         └─ 已滤除 21 条未进入结果的关键词过滤丢弃（未命中包含词 21 条）
```

一个不可见的清洗规则，某天会因一次改版而悄悄删掉大量真实数据，
而没有任何人会发现。

#### 关键词过滤的丢弃计数（2026-10-05 补上）

在补上这个计数之前，**关键词过滤丢弃的条目完全不计数**——只有
`dropped_navigation` 有计数。也就是说：一份标题不含「人工智能」「数据」
等词、正文却含 AI 条款的文件，会被静默丢掉，抓取报告依旧显示 `ok`，
没有任何地方提示「有人被丢了」。

这与导航剔除是同一类问题的两个面，因此补计数只是第一步，还补了两件事：

1. **区分两种原因**。`excluded` 多说明排除词写得太宽（误伤真实政策），
   `not_matched` 多说明包含词写得太窄（漏检 AI 相关文件）——**两者要采取的
   行动完全相反**，只看一个总数无法判断该调哪一边。
2. **留下被丢的条目本身**。`已滤除 151 条` 是一个无法行动的数字：
   维护者既不知道被丢的是《银行业保险业数字金融高质量发展实施方案》
   还是某场表彰大会的新闻稿，也就无从判断该不该改关键词。
   `--show-dropped` 把标题逐条列出来（超过 40 条时显式写明剩余数量，
   不静默截断）。

计数与明细都在抓取报告里，**不写入公开的变更文件**（`data/changes/`）：
变更文件是面向使用者的数据产物，记录「有什么变化」；丢弃统计是抓取期的
诊断信息，记录「流水线做过什么取舍」。把后者塞进前者，会让公开产物里
混进大量与政策无关的标题。

#### 补计数之后立刻抓到两个真实漏检

**其一：`nfra-regulations` 每次 160 条只保留 5 条**（丢弃 155 条）。
把 160 条标题逐条过了一遍，找到 11 条「标题不含现有包含词、但明显与
数字金融/网络治理相关」的条目，再逐词试算每条候选词的新增放行数与噪声：

| 候选词 | 新增放行 | 判定 |
|---|---|---|
| `网络` | 2 条，均应收 | ✅ 采用 |
| `数字` | 2 条，均应收 | ✅ 采用 |
| `网络安全` / `数字金融` | 更窄，会漏掉「网络营销」 | ❌ 太窄 |
| `个人信息` / `信息安全` / `互联网` | 0 条 | ❌ 暂不需要 |

采用后保留数从 5 升到 9，找回的包括
《银行业保险业网络安全管理办法（征求意见稿）》、
《金融产品网络营销管理办法》答记者问（**本项目的金融×AI 交叉点条目，
此前一直被漏掉**）、《银行业保险业数字金融高质量发展实施方案》。

**其二：`csrc-regulations` 每次 144 条只保留 1 条**（丢弃 143 条）。
同样逐条扫描后，指向科技/数据/网络治理的只有 12 条，
其中仅 1 条真正相关：**【第218号令】《证券期货业网络和信息安全管理办法》**。
它规定证券期货机构必须建立网络与信息安全、数据安全、应急响应体系，
任何部署在该行业的 AI 系统都受其约束；而旧词表只有「信息技术」，
匹配不上「网络和信息安全」。加入 `网络` 后新增放行 1 条、零噪声。
其余 11 条经判定不属于本项目范围（6 条是「信息披露」——那是面向投资者的
披露义务，不是数据治理；3 条是「证券登记结算」「基金托管」，与 AI 无关）。

这两个源的新增词完全同构（`网络` / `数字`），因此也在测试里钉住了
**「哪条政策必须被哪个源放行」**这一清单——后来的人看到关键词表里有个
孤零零的「网络」，很可能觉得与 AI 主题不搭而顺手删掉，
那一删就是又一次静默漏检，且没有任何测试会红。

这件事的意义不在于「多加几个词」，而在于：**一个看不见的过滤器，
会让「知识库覆盖不全」与「源头没有这份文件」变得无法区分。**

#### 关键词过滤的匹配范围：标题 + 原样抄录的结构化字段（2026-10-05 修正）

补上丢弃计数之后，计数本身又暴露出第二个问题：**匹配范围太窄。**

关键词过滤原本只匹配 `RawDoc.title`。对政策文件这是够的——标题就是它的身份。
但对罚单不行：罚单的标题是从表格重建的
（`当事人｜违法行为类型（截断到 60 字）`），
而被截掉的部分在标题里就看不见了。

实测数据里最典型的一例：「数据安全」出现在某行违法行为类型的**第 59 个字符**处，
正好被 60 字的截断**切在词中间**——标题里只剩「违反数…」。
用「数据安全」做包含词时，这条记录被判为不相关并丢弃，
丢弃原因显示「未命中包含词」，与「这条罚单确实与数据安全无关」
在报告里长得一模一样。**而且截断点落在词内，人工复核时盯着「违反数…」
也看不出这里本来有一个完整的关键词。**

修正方式是把匹配范围改为「标题 + `extra` 里全部字符串值」
（见 `filter_haystack`）。`extra` 的定义是「从官方页面原样抄录的结构化字段」，
与标题同属来源自己给出的信息，匹配它不引入新的语义。
罚单的 `extra["violation_type"]` 保存的是**未经截断的原文**，
因此截断从此只影响排版，不影响正确性。

修正前后的对照（一条只涉及数据安全的罚单）：

| | 保留 | 丢弃 | 丢弃原因 |
|---|---|---|---|
| 只看标题 | **0 条** | 13 条 | `not_matched: 13` |
| 标题 + `extra` | 1 条 | 12 条 | `not_matched: 12` |

两条规则的范围必须一致：排除规则同样作用于 `extra`。若包含看 `extra`
而排除只看标题，就会出现一个隐蔽的不对称——一份含排除词的文件
仅仅因为标题里没写而侥幸留下。**不对称的规则比两边都窄更危险，
因为它无法用一句话解释。**

这里有一个使用上的陷阱值得写明：若某源的 `extra` 里放了机构名、机关名，
而包含词里又有「银行」这类宽泛词，会命中大量无关记录。
这个风险不是静默的——`excluded` / `not_matched` 的分布会把异常暴露出来。
换句话说，**让匹配范围变宽的前提，是丢弃计数已经可见**；
两件事的顺序不能颠倒。

#### 清洗必须发生在昂贵或不可逆的动作之前（2026-10-05 踩过）

同一个坑还有一个更隐蔽的形态：**清洗的时机。**

罚单抓取器的流程是「先取详情页地址，再逐个打开详情页把表格拆成行」。
而导航链接的清洗（`drop_probable_navigation`）原本由基类在
`_collect()` **返回之后**统一执行——听起来没问题，实际是一次完整的失败运行：

- 列表页选择器 `li:has(span)` 命中了 54 条，其中第 1–34 条是栏目导航
  （「规章」「政府信息公开年报」「2021年」…），第 35–54 条才是真正的「银罚决字」文书；
- 抓取器会先为列表里的每一条打开详情页，于是 20 个 `max_details` 配额
  全被导航吃掉，打开的 20 个页面全是栏目首页，**一页表格也解析不出来**；
- 而清洗仍然照常发生，`dropped_navigation` 也照常计数——
  **数据是干净的，代价已经付掉了。**

修正有两处，缺一不可：

1. **选择器改为 `ul.txtlist li`**——用**容器结构**定位，而不是用
   「含不含某个标签」这种**内容特征**定位。后者的问题在于：它的命中集合
   会随页面内容变化，而导航项恰好满足条件时就会被一起捞进来。
2. **在打开详情页之前就调用清洗**，并把剔除数记进 `_upstream_dropped_navigation`，
   由基类并入 `dropped_navigation`——让「收集阶段剔除的导航」和
   「清洗阶段剔除的导航」在报告里是同一个数字，而不是后者显示 0、
   前者无人知晓。

教训一般化为：**清洗放在流水线后面固然也能让数据变干净，
但它拦不住已经付出的代价。** 凡是「清洗之后才做」的动作里包含
网络请求、不可逆写入、或不可重试的配额消耗，清洗就必须提前到它之前。

#### 变更文件按天累积，同日多次运行必须合并（2026-10-05 修）

同一处「不可见的破坏」的第三种形态：**写文件的时机。**

变更文件按天命名的（`data/changes/YYYY-MM-DD.json`），因此同一天再跑一次
会写到同一个文件上。而写入原本是**整份覆盖**——于是：

```
finreg fetch                              # 全天抓取，产出 55 条
finreg fetch --source csrc-regulations    # 只想重试一个源
# 修复前 → 文件只剩 2 条，另外 53 条无声消失
# 修复后 → 56 条（本次 2 条 + 保留 54 条）
```

危害不在于「丢了几条数据」，而在于它**恰好发生在维护者排查问题的时刻**：
单源运行是最常用的调试动作，调试结束后没人会想到再补跑一次全量，
当天的变更记录就这么永久少了——而变更文件是项目的核心输出。

修复方式是**按自然键合并**而不是覆盖。自然键取
`(change_type, policy_id, url)` 三项：本次产出的条目覆盖同键的旧条目，
本次**没有产出**的旧条目原样保留。

两条设计细节值得写明：

1. **为什么不给变更记录加 `source_id` 然后按源替换**：那会改动公开的变更
   文件格式，而按自然键去重不需要。代价是「同一天内某源产出条数减少时，
   减少掉的那些留在文件里」——这只在**同一天内改动了关键词过滤**时发生，
   而变更文件本身就是「当天观察到什么」的记录，保留并无不妥。
2. **顶层统计必须按合并后的明细重算**。否则文件里会出现
   「`change_count: 1` 而 `changes` 有 40 条」这种自相矛盾的内容——
   这类「文件自己前后不一致」的问题极难发现，因为没有人会去核对一个计数。

合并这件事必须是**可见的**：`fetch` 会打印
`变更文件：2026-10-05.json  共 56 条（本次新增 1、覆盖 1）` 以及
`保留文件中已有的 54 条`，并在文件里写入 `merged_from_previous` 字段。
否则使用者会看到一份「不是本次运行产物」的文件，却以为它是。
既有文件读不出来时也不静默覆盖，而是打印原因后整份重写——
一个损坏的产物不该让整条抓取流水线失败，但这件事必须被说出来。

### 事实性字段不由大模型生成

`status`、`effective_from`、`key_obligations` 等一切描述现实世界事实的字段
一律人工撰写并核验。原因：大模型会生成看似合理但实际错误的日期和条款号，
而这类错误在合规场景中会导致错误的合规结论，且极难被发现。

技术只用于定位页面、格式化、查重。

### 可用配置解决就不写代码

抓取器的选择顺序：`json_search_list`（配置驱动，首选）→ `html_list`
（配置驱动）→ 专用抓取器（最后的选择）。

这条原则在实践中得到了验证：金融监管总局曾被认为「结构特殊、有反爬、
通用方案搞不定」，因此为它写了专用抓取器。后来发现那只是因为**接口地址写错了**——
用对地址后它就是一个标准 JSON 接口，专用抓取器随即被删除。

**大多数「这个站很特殊」的结论，追溯下去往往是「我们还没找对接口」。**

### 测试必须完全离线

政府网站会超时、会改版、会限流。依赖真实网络的测试会变成随机红灯，
最终所有人都学会忽略 CI。

本项目用 `FakeSession` 按 URL 路由到 `tests/fixtures/` 下的**合成**固定装置，
262 个测试在 6 秒内跑完，不产生任何外部请求。

### 不用 LangChain / 向量库 / Web 框架

运行时依赖只有六个：`requests`、`beautifulsoup4`、`lxml`、`PyYAML`、
`jsonschema`、`python-dateutil`。

本项目定位是「三年后依然能跑起来」的长期基础设施。每减少一个依赖，
就少一个未来破坏兼容性的风险点。

## 常见问题

**Q：为什么不用大模型直接读政策原文、自动生成结构化记录？**

因为这正是产生「看起来对、实际错」数据的最高效方式。一个编造的
「已于某日废止」能让企业白做一轮整改。技术可以用来定位和格式化，
但事实必须人工确认。

**Q：为什么有些记录的状态是 `effective`，但 `effective_from` 是空的？**

因为该文件的施行日期确实无法确认（官方原文未载明，或原文页面不可访问）。
本项目选择显式承认「不知道」，而不是编造一个日期。
这类记录会带警告提示，并在 `verified_note` 中说明障碍。

**Q：我发现一条记录有错，怎么办？**

欢迎提 Issue 或直接提 PR。请附上官方页面链接与你的核对过程。
如果多个来源互相矛盾，请把矛盾写进 `verified_note`——
承认不确定性本身就是有价值的信息。

**Q：数据可以商用吗？**

可以。数据采用 CC BY 4.0（署名即可，含商业用途），代码采用 MIT。
但请注意，政策文件原文的著作权状态与本项目许可证无关，
详见 `DATA_LICENSE.md`。

**Q：为什么只做中国？**

因为这是本项目最有价值的地方。EU/US 的监管追踪已有多个成熟项目，
而「中国 + 金融 + AI 合规 + 实时 + 机器可读」这个交集是空的。
