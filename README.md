# finreg-ai-cn

**中国金融领域 AI 合规政策知识库** —— 机器可读、带时效性治理、可溯源。

检索当前有效的 AI 合规政策，聚焦银行业、证券期货业、保险业与支付清算领域。
每条记录都标注**此刻是否有效**、**被谁取代**、**最近何时核验过**。

## 这个项目解决什么问题

中国金融领域的 AI 合规要求散落在多个监管机构的数百份文件中：
人民银行、金融监管总局、证监会、网信办、工信部，以及各类行业自律组织。
对一家中小金融机构而言，真正的困难不是「找不到文件」，而是三个更具体的问题：

1. **这份文件现在还有效吗？** —— 政策常被修订、取代、废止，但绝大多数
   资料库只保留最新版，不记录版本链。
2. **它到底要求我做什么？** —— 原始文件动辄三四十条，其中真正产生义务的
   可能只有十几条，需要逐条提炼。
3. **我凭什么相信这条记录是对的？** —— 没有核验时间戳与官方链接的
   「知识库」，本质上只是一个不可验证的传言集合。

本项目的目标就是把这三个问题变成可查询的数据。

## 时效性治理是怎么做的

这是本项目的核心机制，也是与「爬虫 + 全文检索」类方案的根本区别。

### 1. 状态是核验出来的，不是推断出来的

`status` 取十个受控值之一：`draft` / `consultation` / `published` /
`effective` / `partially_effective` / `amended` / `repealed` /
`superseded` / `expired` / `unknown`。

注意 `amended`（已修订，新版有效）与 `partially_effective`（部分有效）
**都算「当前有效」**——它们是「有效但需注意版本」，与「已废止」有本质区别。

### 2. 版本链而非快照

每条记录通过 `supersedes` / `superseded_by` / `amends` / `amended_by`
组成有向链，且**双向指针必须闭合**：声称被某文件取代，那个文件就必须在库中存在。
校验器会强制检查这一点。

合规审查经常要判断「**当时**适用的是哪一版、**当时**的义务是什么」。
只保留最新版的知识库无法回答这个问题，因此本项目保留整条版本链。

### 3. 允许「不知道」，且要求显式承认

如果一条记录现行有效但施行日期无法确认，`effective_from` 应当留空，
并在 `verified_note` 中说明原因。这会产生一条**警告**（不阻断），
而不是**错误**（阻断）。

这个分级是刻意的：如果把「缺日期」判为错误，维护者会被迫编造一个日期
来让校验通过——**那才是对数据质量真正的伤害**。

这条纪律由两条校验规则执行：

| 规则 | 触发条件 | 级别 |
|---|---|---|
| **规则 11** | `effective_from` 非空，但 `verified_note` 承认该日期尚未确认 | **错误**（阻断） |
| **规则 12** | `verified_by=automated` 且 `effective_from` 非空，但说明未交代日期出处 | 警告 |

规则 11 判为错误而非警告，是因为它描述的不是「信息缺失」而是「信息自相矛盾」——
缺失是显式的空白（使用者会去问），矛盾却会静默地变成一条假事实。

判定方式是**句内绑定**：只有当「生效日期」这个话题与「不确定」这种表态出现在
**同一句话**里才算矛盾，否则一条说明里讲配套细则「尚未明确」也会被误报。
规则 12 只约束自动整理的记录，因为「把字段填满」是自动化产出的结构性倾向，
而人工核验过的记录，核验行为本身就是依据。

**这条机制是启发式护栏，不是证明。** 它能拦住「承认了却仍填值」这一种形态，
拦不住「悄悄编一个日期且全文不提任何不确定」——后者与诚实填写的记录
在字面上无法区分，只能靠人工核对原文。这也正是 `last_verified` 台账与
`verified_by` 字段存在的理由。

### 4. 陈旧记录自动浮出

`last_verified` 记录最近一次核验日期。超过 180 天未核验的记录会在
`finreg validate` 中列出、进入 `finreg stale` 的待办清单，
并由配套的 GitHub Actions 工作流每日自动检查。

## 快速开始

```bash
# 安装（含开发依赖）
pip install -e ".[dev]"

# 看看现在有效的政策有哪些
finreg list --effective-only

# 查看某条记录的完整信息（含逐条义务）
finreg show nfra-2026-ai-guidance

# 执行抓取，发现新政策（不写盘）
finreg fetch --dry-run

# 校验仓库数据完整性
finreg validate

# 列出超期未核验的记录（时效性治理的核心工具）
finreg stale

# 预演：看看再过一个月，哪些记录会进入待核验队列
finreg stale --days 30 --as-of 2027-01-01

# 生成对外展示的静态站点（输出到 docs/）
finreg build-site
```

不需要克隆仓库也可以直接用数据：所有记录都是普通 YAML 文件，
在 `data/policies/` 目录下。

### 全部命令

| 命令 | 作用 |
|---|---|
| `finreg list` | 列出政策记录，支持按状态 / 机构 / AI 相关度 / 主题筛选，`--json` 可机读 |
| `finreg show <id>` | 查看单条记录的完整信息，含逐条关键义务与条号 |
| `finreg stale` | 列出超期未核验的记录。`--days N` 设阈值（默认 180），`--as-of YYYY-MM-DD` 指定基准日 |
| `finreg fetch` | 执行抓取流水线，发现新政策并产出变更流。`--dry-run` 只报告不写盘，`--show-dropped` 列出被关键词过滤丢弃的条目，`--force` 允许运行未启用的源（`--source` 指定） |
| `finreg validate` | 校验全部数据的完整性（CI 门禁） |
| `finreg validate-sources` | 只校验数据源登记表 `data/sources.yaml` |
| `finreg build-site` | 从 `data/` 生成静态站点（对外只读视图）。`--output DIR` 换输出位置，`--json` 输出构建结果 |

#### `stale --as-of` 为什么存在

判定「某条记录是否超期未核验」必须有一个基准日，默认取北京时间今天。
把它做成可传入的有两个用途：

1. **预演**——想知道「再过 60 天哪些记录会进入待核验队列」，直接传未来日期即可，
   不必等到那天。
2. **测试可重复**——测试不应隐含地以「今天」为基准，否则断言会随时间自行失效，
   而代码一行没改。

```bash
# 今天的视角
$ finreg stale --days 30
没有超过 30 天未核验的记录。

# 快进到 2027-01-01 的视角（会显式回显基准日）
$ finreg stale --days 30 --as-of 2027-01-01
共 9 条记录超过 30 天未核验（基准日 2027-01-01）：

  cac-2022-algorithm-recommendation         90 天    状态=effective
    └─ https://www.cac.gov.cn/2022-01/04/c_1642894606364259.htm
  ...
```

### 输出示例

```
$ finreg list --effective-only

共 8 条记录：

  cac-2022-algorithm-recommendation      effective            2022-03-01  互联网信息服务算法推荐管理规定
  cac-2023-genai-interim-measures        effective            2023-08-15  生成式人工智能服务管理暂行办法
  nfra-2026-ai-guidance                  effective            2026-XX-XX  关于银行业保险业人工智能安全开发应用的指导意见
  ...
```

> 注意上例中 `nfra-2026-ai-guidance` 的生效日期显示为待核验状态。
> 本项目宁可显示「日期待核验」，也不填一个未经证实的日期。

## 数据模型（字段字典）

一条记录的完整结构见 `schema/policy.schema.json`。核心字段说明如下。

### 身份

| 字段 | 说明 |
|---|---|
| `id` | 全局唯一标识，格式 `<机构代码>-<年份>-<语义化短名>` |
| `title` | 官方全称，必须与官方页面标题完全一致 |
| `issuer` | 发布机构全称；多部门联合发布时用顿号分隔 |
| `issuer_code` | 机构代码，须在 `data/sources.yaml` 的 `issuers` 中登记 |
| `doc_number` | 发文字号，如 `银发〔2023〕89号` |

### 效力（两个正交维度）

| 字段 | 取值 | 说明 |
|---|---|---|
| `instrument_type` | `法律` / `行政法规` / `部门规章` / `部门规范性文件` / `行业自律规则` / `国家标准` / `地方性文件` / `其他` | 这是什么级别的文件 |
| `bindingness` | `binding` / `soft-law` / `guidance` / `consultation` | 它是否产生强制义务 |
| `ai_relevance` | `core` / `related` / `background` | 与 AI 合规主题的相关度 |

**为什么要把这两个维度分开**：一份「指导意见」在文件层级上只是部门规范性文件，
但其正文中的「须」「不得」「严禁」对应实质义务，违反同样会招致监管措施。
只看文件层级会严重低估合规压力。

### 时效（核心）

| 字段 | 说明 |
|---|---|
| `status` | 法律状态，十个受控取值之一 |
| `published_on` | 官方发布日期（注意区别于成文日期，二者常不同） |
| `effective_from` | 施行日期；无法确认时留空并在 `verified_note` 说明 |
| `effective_until` | 失效日期；多数文件为 `null`，需主动核验 |
| `supersedes` / `superseded_by` | 取代关系，双向指针必须闭合 |
| `amends` / `amended_by` | 修订关系，同上 |
| `versions[]` | 版本历史，每条含独立的日期、状态与原文链接 |

### 溯源

| 字段 | 说明 |
|---|---|
| `source.url` | 官方页面链接，**必须**可公开访问 |
| `source.tier` | 来源等级，**必须**为 `primary` |
| `source.fetched_at` | 抓取时间（带 `+08:00` 时区） |
| `source.content_hash` | 正文 SHA-256 摘要，用于检测内容变更 |
| `last_verified` | 最近一次核验日期 |
| `verified_by` | `human`（人工逐项核对）或 `automated`（仅自动确认可访问） |
| `verified_note` | 核验过程说明；状态为 `unknown` 或核验遇阻时**必须**填写 |

### 内容

| 字段 | 说明 |
|---|---|
| `topics[]` | 主题标签，取自受控词表 |
| `applicable_to[]` | 适用主体清单 |
| `key_obligations[]` | 关键义务，每条含 `clause`（原文条款定位）与 `summary`（人工撰写的概括） |

### 第二种数据类型：执法记录（罚单）

政策文件回答「**应该怎么做**」，行政处罚记录回答「**没这么做会怎样**」。
两者的字段结构、来源形态、可信度判断方式都不同，因此是两个独立的
数据类型与两份独立的 schema，而不是把罚单塞进政策记录里凑合。

| | `data/policies/` | `data/enforcement/` |
|---|---|---|
| 回答的问题 | 应该怎么做 | 没这么做会怎样 |
| 谁产生 | 机器发现 + **人工提炼义务** | 机器抄录 + **人工认定收录** |
| 可信度怎么判断 | 是否逐条对照过原文 | 字段是抄的还是核过的 |
| 更新节奏 | 低频（每年数十条） | 中频（人民银行一次公示可覆盖十几家机构） |

**它的核心用途是校验政策侧的义务清单。** 政策里的 `key_obligations`
是人工从原文提炼的，提炼得对不对无从验证；而罚单里「违反数据安全管理规定」
这样的表述，直接说明监管实际在查什么。两者对照才能回答三个问题：

1. **义务清单写全了吗？** 监管在处罚某类行为，而我们的义务清单里没有对应条目。
2. **写了的东西监管真的查吗？** 义务清单里写了，罚单里从没出现过同类违规。
3. **中小机构实际栽在哪？** 罚单的当事人类型与违规类型分布，是「客户痛点」
   最直接的证据。

因此 `related_policies` 是本类型**最重要的一个字段**——它把「违规事实」与
「对应义务」连起来。空着也能用（罚单本身仍可检索），但只有填了，
知识库才真正具备反向校验义务清单的能力。它的引用闭合由 `finreg validate`
机械校验：指向一条不存在的政策会直接报错。

一条与政策记录不同的纪律：**官方行政处罚公示不含「处罚依据」条款**
（人民银行公示表格只有违法行为类型、处罚内容、决定机关、决定日期等列）。
因此 `legal_basis` 默认就是空的，**这不是缺失而是事实**。
绝不从「违反数据安全管理规定」倒推出「违反了《数据安全法》第 X 条」——
那种倒推是一条没有出处的推断，一旦写进记录就会和官方原文混在一起，
使用者无法分辨哪条是抄的、哪条是猜的。

抓取侧已可用（`finreg fetch --source pbc-administrative-penalties --force`），
但 `data/enforcement/` 目录当前为空——因为录入标准依赖尚未建立的
「判定规则层」，详见 [`data/enforcement/README.md`](data/enforcement/README.md)。

| `manual-entry` | 任意 | ✅ 兜底通道 | 人工录入，用于无法自动抓取的来源 |

| `most-ai-ethics` | 科技部 | ⏸ 未启用 | 第二梯队 |
| `tc260-ai-standards` | TC260 | ⏸ 未启用 | 第二梯队 |
| `sac-self-regulation` | 中证协 | ⏸ 未启用 | 第三梯队 |
| `shanghai-ai-policy` | 上海市 | ⏸ 未启用 | 第三梯队 |

> 为什么停用 `nfra-consultations` 而不是凑合着用：配置里的栏目 id 返回的是
> 「交强险业务公告」「拟录用公务员公示」等无关文件，与「征求意见稿」完全无关。
> 若保留该配置，征求意见稿分类里会混入大量无关公告，而抓取状态仍是 `ok`，
> **没有任何机制会提示异常**——这属于静默污染，比抓不到更危险。

> **`pbc-regulations` 保留 0 条不是故障。** 抓取报告会区分「源坏了」与
> 「源头确实没有」：本次正常解析出的条目全部是《中国人民银行公告〔2026〕第N号》、
> 跨境资金集中运营、境外贷款等与 AI 无关的文件，因此保留数为 0 是正确结果。
> 源是活的，只是最近这批确实没有 AI 内容。

## 对外展示：静态站点

站点是 **git 数据的一个视图**，不是一个独立的应用。

```bash
finreg build-site                              # 生成到 docs/
finreg build-site --output /tmp/site-preview   # 换个位置，随手可删

# 本地预览。必须走 HTTP：直接 file:// 打开会让相对路径与脚本行为不一致
cd docs && python -m http.server 8000
```

发布走 `.github/workflows/pages.yml`：CI 里构建、以 Pages 产物形式上传。
`docs/` 是**构建产物**，已写进 `.gitignore`，不入库。

仓库侧需先把 Pages 的 Source 设为「GitHub Actions」——这是**一次性**设置，
且**需要仓库管理权限**：Settings → Pages → Source，或一条
`POST /repos/{owner}/{repo}/pages` 调用。默认的 workflow 令牌不含
`administration` 权限，无法替仓库完成这一步；此后每次推送由 `pages.yml`
自动构建与部署，无需再动。

### 为什么没有数据库

因为这个项目不需要，而且加了会更糟。

规模上就不成立：9 条政策、`data/` 全量合计 222 KB，一次 HTTP 请求就下完了。
数据库真正解决的问题是「数据装不进内存」「多人并发写」「需要事务」
「按用户隔离数据」——这四条本库一条都不占。

而引入它的代价，恰好全部落在这个项目自己的立足点上：

| 引入数据库的后果 | 失去什么 |
| --- | --- |
| 出现第二个真相源 | 「版本溯源」失去依据——一旦与 git 分叉，无法回答「以哪个为准」 |
| 写入不再经过 PR | 人审闸门失效——「机器发现，人认定」这条纪律是靠 diff 运转的 |
| 需要一台常驻服务 | 违反「GitHub Actions 定时跑，不上服务器」这条承载决策 |
| 别人克隆后跑不起来 | 开源项目的可分叉性——`pip install && finreg validate` 应当直接可用 |

于是前端做成**静态站**：`data/` → 生成器 → `docs/` → Pages。
检索也不需要服务端：政策全量塞进页面，用客户端子串匹配即可
（中文按子串匹配天然可用，不必分词）。数据涨到几百条以上再谈索引方案。

### 站点只做三件竞品给不出的事

法规汇编满地都是。站点若只是「把 YAML 渲染成表格」就没有存在的理由，
因此重点全压在这三条别人给不出的信息上：

1. **变更流** —— 直接渲染 `data/changes/*.json`。这是全项目唯一的「活」证据；
   页面同时写明「这些条目尚未经人工认定」，不让机器的一次关键词命中
   冒充成合规事实
2. **版本链时间轴** —— 把 `supersedes` / `effective_from` / `effective_until` /
   `status` 画成一条线。**别人给快照，这里给演进**
3. **待核验缺口** —— 「现行有效但查不到施行日期」在页面上被显式标出，
   而不是留白等人误读

### 站点没有自己的数据

生成器读的就是 `data/`，页面上没有任何人工单独维护的内容。
这条性质由测试钉死：`tests/test_site.py` 断言
**同一份数据 + 同一时间戳 → 逐字节相同的产物**。
哪天页面变了却说不清是哪份数据变的，那条测试会先红。

## 自动化（GitHub Actions）

仓库自带三套工作流，各管一件事：

| 工作流 | 触发时机 | 做什么 |
| --- | --- | --- |
| `validate.yml` | 推送主干、每个 PR、手动 | 三个并行作业：代码质量（ruff + mypy）、跨 4 个 Python 版本跑测试、数据完整性校验 |
| `fetch.yml` | 每天北京时间 06:00、手动 | 抓取各监管机构官网，把新发现写入 `data/changes/` 并自动提交 |
| `pages.yml` | 推送主干（数据 / 代码 / 前端资源变动）、抓取流程跑完后、手动 | 构建静态站并发布到 GitHub Pages |

`pages.yml` 为什么额外挂了一个「抓取流程跑完后」的触发：`fetch.yml` 用
`GITHUB_TOKEN` 推送，而**这种推送不会触发 `push` 事件驱动的工作流**。
只写 `on: push` 的话，每天抓到的新数据永远不会让站点重新发布。
因此它同时监听 `workflow_run`（在某个流程运行结束时触发，与是谁触发的无关）。

依赖按 `requirements.txt` / `requirements-dev.txt` 中的**精确版本**安装，
而不是用 `pip install -e ".[dev]"`：`pyproject.toml` 里的约束是范围（`>=`），
上游一发新版就可能让 CI 因为与本项目无关的原因变红。

### 自动化的边界：它不碰 `data/policies/`

`fetch.yml` 只会写入并提交 `data/changes/`，**绝不会修改 `data/policies/`**。
这是刻意的：

- 抓取器负责**发现**，人负责**认定**
- 结构化记录里的每个字段值都必须由人从官方原文中读出来。
  让程序直接往里写记录，等于把「不可核验」引进了知识库的根子上——
  而「可核验」正是本项目区别于二手汇编的唯一理由
- 所以 `data/changes/` 里是**候选**，未经核验，不能作为合规依据

### 源失效会被追着问，不会悄悄过去

如果某个源本次返回 `failed` 或 `degraded`，工作流会：

1. 把该源连同错误详情写进 Actions 的**任务摘要**（打开流程页面即可见，不必翻日志）
2. 自动开一个 issue 跟踪；若已有未关闭的同类 issue，则改为追加评论——
   保留完整时间线，能看出问题是持续的还是偶发的，也避免每天开一个新的把列表刷满

`degraded` 同样会上报，而且更需要上报：它的含义是「抓取器跑通了，
但一条都没解析出来」。这正是站点改版的典型征兆——**看起来成功，实际是失明**。

### 运维注意点

**1. 首次启用请先手动触发一次。** GitHub 的运行器在境外，部分中国政府网站
可能存在境外访问缓慢甚至被拒绝的情况。若某个源稳定报 `failed`，应改为在境内
机器上手动抓取，而不是让它每天刷一条失败记录。手动触发时可以填 `source`
只抓单个源，或勾选 `dry_run` 试跑而不写文件。

**2. 机器人提交不会触发 `validate.yml`。** 用内置 `GITHUB_TOKEN` 产生的推送
**不会触发其他工作流**（GitHub 为防止递归触发而如此设计）。因此 `fetch.yml` 把
`finreg validate` 放在**提交之前**作为闸门——否则机器人就拥有了一条绕过校验的
提交通道。不要随意删掉那个「校验数据完整性（提交前闸门）」步骤。
同一条限制也影响站点发布：`pages.yml` 的 `on: push` 不会被机器人的提交唤起，
因此它额外监听 `workflow_run`（`fetch.yml` 跑完即触发）。

**3. 主干若开了分支保护。** 机器人会被拒绝推送，`fetch.yml` 的提交步骤会失败。
两种处理方式：把机器人加入允许直接推送的名单，或者把 `fetch.yml` 改成提 PR
由人合并。不建议为了迁就自动化而关闭分支保护。

### mypy 为什么只检查 `src`

会被别人 import 的代码（`src`）有严格类型保证；`tests` 由「真的把它跑起来」
（pytest）加 ruff 两层覆盖。不把 `tests` 纳入 mypy，是因为解析 tests 的导入链时
会走进 site-packages，撞上 numpy `.pyi` 存根里 Python 3.12+ 语法的类型声明，
而本项目声明的 `python_version` 是 3.10——那是第三方存根的问题，
为它放宽自己的检查尺度不值得。

注意 `tests/` 必须保留 `__init__.py`：其中有 `from tests.conftest import ...`，
缺了这个文件在 Linux CI 上会收集失败（退出码 2）。

## 设计原则

### 单源失效不拖垮整体

每个抓取器都被独立隔离，任何异常都转成 `FetchResult(status="failed")`，
绝不会向上冒泡中断流水线。失败源会被记入报告与变更流，**而不是静默消失**。

### 明确失败优于静默错误

这是本项目最重要的一条。抓取器最危险的失败方式不是崩溃，而是「成功地」
抓回一堆垃圾——导航链接、统计数据、页脚备案号——同时流水线报告 `status=ok`。
使用者看到「今天没有新政策」，而真相是抓取坏了。

具体对策：

- **0 条报 `degraded` 而非 `empty`**：因为无法区分「确实没有新政策」
  与「选择器失效了」
- **结果质量自检**：标题平均长度过短说明抓到的是导航链接；
  日期命中率过低说明字段映射已失效
- **站点自检**：政府网站改版后旧 URL 常被重定向到首页而非返回 404，
  此时应主动失败而不是「成功」抓到首页导航

### 清洗与变更流的四条纪律

**1. 剔除任何条目都必须可见。** 剔除数量要出现在抓取报告里，
否则一个清洗规则某天会因一次改版而悄悄删掉大量真实数据，没有任何人会发现。

```
[OK]     pbc-regulations          条目数=0
         ├─ 已剔除 5 条疑似栏目导航链接
         └─ 已滤除 21 条未进入结果的关键词过滤丢弃（未命中包含词 21 条）
```

丢弃还要分两种原因：`excluded`（命中排除词，误伤真实政策）与 `not_matched`
（未命中包含词，漏检 AI 相关文件）——两者该采取的行动完全相反，只看总数无法判断
该调哪一边。`--show-dropped` 会把被丢条目的标题逐条列出（超过 40 条时显式写明
剩余数量，不静默截断）。

**2. 关键词过滤的匹配范围 = 标题 + 原样抄录的结构化字段。** 罚单标题是从表格重建
并截断到 60 字的，只看标题会让出现在截断点之后的关键词被切在词中间而静默漏检。
因此匹配范围扩展到 `extra` 里全部字符串值（`extra` 保存的是未经截断的原文），
截断从此只影响排版、不影响正确性。包含与排除规则的作用范围必须一致：若包含看
`extra` 而排除只看标题，一份含排除词的文件会仅仅因为标题里没写而侥幸留下。

**3. 清洗必须发生在昂贵或不可逆的动作之前。** 罚单抓取器要逐个打开详情页，
如果先打开详情页再清洗导航链接，详情页配额会全被导航吃掉，一页表格也解析不出来。
凡是「清洗之后才做」的动作里包含网络请求、不可逆写入或不可重试的配额消耗，
清洗就必须提前到它之前。同理，定位条目要依赖**容器结构**而非「含不含某个标签」
这种内容特征——内容特征的命中集合会随页面内容变化。

**4. 变更文件按天累积，同日多次运行必须合并。** 变更文件按天命名
（`data/changes/YYYY-MM-DD.json`），同一天再跑一次会写到同一个文件上。
写入按自然键 `(change_type, policy_id, url)` 合并而不是整份覆盖：本次产出的条目
覆盖同键的旧条目，本次没有产出的旧条目原样保留。顶层统计必须按合并后的明细重算，
否则文件里会出现「`change_count` 与 `changes` 条数不符」这种自相矛盾的内容。
合并是可见的：`fetch` 会打印本次新增 / 覆盖 / 保留的条数。

计数与丢弃明细都在抓取报告里，**不写入公开的变更文件**（`data/changes/`）：
变更文件是面向使用者的数据产物，记录「有什么变化」；丢弃统计是抓取期的诊断信息，
记录「流水线做过什么取舍」。把后者塞进前者，会让公开产物里混进大量与政策无关的标题。

### 事实性字段不由大模型生成

`status`、`effective_from`、`key_obligations` 等一切描述现实世界事实的字段
一律人工撰写并核验。原因：大模型会生成看似合理但实际错误的日期和条款号，
而这类错误在合规场景中会导致错误的合规结论，且极难被发现。
技术只用于定位页面、格式化、查重。

### 可用配置解决就不写代码

抓取器的选择顺序：`json_search_list`（配置驱动，首选）→ `html_list`
（配置驱动）→ 专用抓取器（最后的选择）。「这个站很特殊」的结论，
追溯下去往往是「还没找对接口」。

### 测试必须完全离线

政府网站会超时、会改版、会限流。依赖真实网络的测试会变成随机红灯，
最终所有人都学会忽略 CI。本项目用 `FakeSession` 按 URL 路由到
`tests/fixtures/` 下的**合成**固定装置，298 个测试在 4 秒内跑完，
不产生任何外部请求。

站点生成器同样可测：`build_site` 的政策、变更、时间戳全部可注入，
断言直接落在写出的**字节**上。其中一条是**确定性**测试：同一份数据 +
同一时间戳必须产出逐字节相同的产物——不注入时间戳，就说不清「页面变了」
是因为数据变了还是因为跑的时间变了。

### 不用 LangChain / 向量库 / Web 框架 / 数据库

运行时依赖只有六个：`requests`、`beautifulsoup4`、`lxml`、`PyYAML`、
`jsonschema`、`python-dateutil`。前端同理：没有 Node 构建步骤、没有 npm 依赖、
没有 CDN 引用，样式与检索脚本是两个手写文件（`site/assets/`）。
理由不是「反技术」，而是这个项目的数据量（222 KB）和明确需求（把已有数据展示出来）
都不需要更重的东西——多一个依赖就多一个未来可能失效的点。
本项目定位是「三年后依然能跑起来」的长期基础设施。
数据库为什么不需要，见上文「对外展示：静态站点」。

## 常见问题

**Q：为什么不用大模型直接读政策原文、自动生成结构化记录？**

因为这正是产生「看起来对、实际错」数据的最高效方式。一个编造的
「已于某日废止」能让企业白做一轮整改。技术可以用来定位和格式化，
但事实必须人工确认。

**Q：为什么有些记录的状态是 `effective`，但 `effective_from` 是空的？**

因为该文件的施行日期确实无法确认（官方原文未载明，或原文页面不可访问）。
本项目选择显式承认「不知道」，而不是编造一个日期。
这类记录会带警告提示，并在 `verified_note` 中说明障碍。

**Q：我发现一条记录有错，怎么办？**

欢迎提 Issue 或直接提 PR。请附上官方页面链接与你的核对过程。
如果多个来源互相矛盾，请把矛盾写进 `verified_note`——
承认不确定性本身就是有价值的信息。

**Q：数据可以商用吗？**

可以。数据采用 CC BY 4.0（署名即可，含商业用途），代码采用 MIT。
但请注意，政策文件原文的著作权状态与本项目许可证无关，
详见 `DATA_LICENSE.md`。

**Q：为什么只做中国？**

因为这是本项目最有价值的地方。EU/US 的监管追踪已有多个成熟项目，
而「中国 + 金融 + AI 合规 + 实时 + 机器可读」这个交集是空的。
