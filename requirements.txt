# ============================================================
# 运行时依赖 —— 抓取、解析、校验流水线所需的最小集合
# 设计原则：依赖越少，长期可维护性越好。本项目刻意不引入
# LangChain / 向量数据库 / Web 框架，因为这些属于消费端，
# 不属于知识库内核。内核必须能在三年后依然跑得起来。
# ============================================================

# HTTP 请求库 —— 用于访问各监管机构官网
# 选它而非 urllib 的原因：连接池、超时控制、重试策略、Session 复用都开箱即用，
# 而这些对「批量抓几十个政府网站且不能互相拖垮」是刚需
requests==2.32.3

# HTML 解析器 —— 从政府网站列表中提取标题、链接、日期
# 选 BeautifulSoup 而非 lxml 直接操作的原因：政府网站 HTML 质量普遍很差
# （标签未闭合、属性缺失），BeautifulSoup 的容错解析能力明显更强
beautifulsoup4==4.12.3

# BeautifulSoup 的高性能解析后端
# 比内置 html.parser 快约 10 倍，且对畸形 HTML 的修复更接近浏览器行为。
# 锁 6.1.3：5.3.0 内嵌的 libxml2 带有已在上游修复的安全问题，
# 升级后已跑全量离线测试（303 项）确认解析行为无回归
lxml==6.1.3

# YAML 读写 —— 本项目所有政策记录与数据源登记表均使用 YAML 存储
# 选 YAML 而非 JSON 的原因：支持行内注释，这对「每条数据都要能自我解释」
# 的合规知识库至关重要；JSON 无法承载注释
PyYAML==6.0.2

# JSON Schema 校验 —— 保证每条政策记录的结构合法
# 这是本项目的核心质量闸门：数据结构一旦漂移，下游所有消费方全部失效
jsonschema==4.23.0

# 日期解析 —— 政府网站日期格式极其混乱（2026-06-18 / 2026年6月18日 / 26.6.18）
# 用成熟库处理而非手写正则，减少边界情况出错
python-dateutil==2.9.0.post0

# PDF 文本提取 —— 核验层的附件取证（公告+附件型发布的实体内容在 PDF 里）
# 选 pypdf 的原因：纯 Python、无 C 扩展，任何环境都能装；本需求只是
# 「提取文字型 PDF 的文本」，用不到 pdfminer 的版面分析能力。
# 这是 C 线「零新增依赖」约束的唯一例外，经用户 2026-10-08 明确批准
# （原则：尽量自动化，人只做确认）；扫描件图片 PDF 不做 OCR，标失败转人工
pypdf==6.19.0
