# data/enforcement —— 执法记录（罚单）

这个目录存放**行政处罚记录**，是本项目区别于「政策文件」的第二种数据类型。

一句话说明两者的关系：

| | 回答的问题 | 谁产生 | 可信度怎么判断 |
|---|---|---|---|
| `data/policies/` | 应该怎么做 | 机器发现 + **人工提炼义务** | 是否逐条对照过原文 |
| `data/enforcement/` | 没这么做会怎样 | 机器抄录 + **人工认定收录** | 字段是抄的还是核过的 |

## 为什么罚单值得单独收

政策里的义务清单是人工从原文提炼的，提炼得对不对**无从验证**；
而罚单里「违反数据安全管理规定」这样的表述，直接说明监管实际在查什么。
两者对照，才能回答三个用它才能回答的问题：

1. **义务清单写全了吗？** 监管在处罚某类行为，而我们的义务清单里没有对应条目 → 漏了。
2. **写了的东西监管真的查吗？** 义务清单里写了，罚单里从没出现过同类违规 → 要么写得太虚，要么优先级排错了。
3. **中小机构实际栽在哪？** 罚单的当事人类型、违规类型分布，是「客户痛点」最直接的证据，
   比任何调研访谈都硬。

因此 `related_policies` 是本目录里**最重要的字段**——它把「监管实际处罚的行为」
连到「我们提炼出的义务」。空着也能用（罚单本身仍可检索），
但只有填了，知识库才真正具备反向校验义务清单的能力。

## 收录规则

### 抓取器不写这里

抓取器只把公示表格的原始行写进 `data/changes/YYYY-MM-DD.json` 的 `extra` 字段。
**它从不写 `data/enforcement/`。** 与「抓取器绝不写 `data/policies/`」是同一条原则：
机器负责发现，人负责认定。

原因是具体的：机器看到的是一张表格里的一行，它能确定「这一行是这么写的」，
但不能确定「这条罚单值得进库」。很多罚单与 AI 合规毫无关系
（如违反反假货币业务管理规定），把它们全收进来会让库变成法规原文的复印件。

### 「认定」与「核验」不是一件事

一条记录可以**已被认定收录、但字段尚未逐字核对**。这是合法状态，处理方式是把
`verified_by` 写成 `automated`，并在 `notes` 里写明抄录范围。
`verified_by` 记录的是**字段值是如何确认的**，不是「谁决定收录它」。

这条区分是刻意保留的：如果只有「人工逐字核过」才允许入库，
那么第一批记录就得靠手抄，而手抄恰恰是最容易引入错别字的方式。

### 三条纪律

1. **官方公示不含处罚依据，`legal_basis` 默认就是空的。**
   实测人民银行公示表格只有违法行为类型、处罚内容、决定机关、决定日期、公示期限等列。
   绝不从「违反数据安全管理规定」倒推出「违反了《数据安全法》第 X 条」——
   那种倒推看起来很有价值，但它是一条**没有出处的推断**，
   一旦写进记录就会和官方原文混在一起，使用者无法分辨哪条是抄的、哪条是猜的。
   若确实另查到了依据，**必须在 `notes` 里写明出处**（校验器会检查这一点）。

2. **不知道就留空，不要为了完整而填。**
   `domain`、`party_type`、`related_policies` 留空是正常的；
   填错了比空着危害大得多，因为它会进入聚合统计。

3. **金额、日期一律原样抄录。**
   「警告，没收违法所得1.621747万元，罚款1712.4万元」就照抄这句，
   不要拆成结构化数字；「2026年9月8日」保留中文写法，不要转 ISO 格式。
   原文的表述方式本身就是信息（是否写明具体数额、是警告还是罚款），
   解析会把它压平。

## 一条记录的完整流程

```text
1. 抓取       finreg fetch --source pbc-administrative-penalties --force
              → 发现的新文书与逐行抄录的字段进入 data/changes/YYYY-MM-DD.json
                的 extra 字段（含当事人、文号、违法行为类型、处罚内容等）

2. 判断       人读变更流，判断哪几条与本项目关注的范围相关
              → 判断标准目前以「违法行为类型是否涉及数据、信息、网络、
                科技、算法、智能、技术」为主，辅以是否触及金融业务本身

3. 录入       在 data/enforcement/ 下新建 <id>.yaml，字段从变更流的 extra 抄录
              → id 格式见 schema：<issuer_code>-<年份>-<文号短名>，如 pbc-2026-yinfa-104
              → 文件名为 <id>.yaml，与 id 一一对应

4. 关联       （可选，但这是本目录的价值所在）把 related_policies 填上对应的政策 id
              → 前提是该项目已经存在对应的政策记录；政策里还没有这一条时，
                先补政策，再回来填关联

5. 校验       finreg validate
              → 结构、语义、引用闭合三层校验；引用不存在的政策会被拦下
```

### 最小可用记录

下面这份可以直接抄去改。注意 `legal_basis` 与 `domain` 留空是**正确状态**，
不是没写完；`notes` 里那句关于抄录范围的说明是 `verified_by: automated` 的必填交代。

```yaml
# 记录唯一标识，格式 <issuer_code>-<年份>-<文号短名>
id: pbc-2026-yinfa-104
# 行政处罚决定书文号，与官方公示完全一致（含括号形式）
decision_no: 银罚决字〔2026〕104号
# 被处罚当事人名称，原样抄录；个人当事人通常已被官方脱敏为「蒋某」
party: 某某银行股份有限公司
# 当事人类型：institution / individual / unknown
party_type: institution
# 违法行为类型，原样抄录官方表述，多项时保留原貌
violation_type: 1.违反金融统计管理规定; 2.违反数据安全管理规定
# 行政处罚内容，原样抄录，不拆成金额数字
penalty_content: 警告，罚款100万元
# 作出行政处罚决定的机关名称
authority: 中国人民银行
# 处罚依据。官方公示通常不提供，留空即为正确，理由见本文件「三条纪律」
legal_basis: null
# 作出决定日期，保留官方页面的中文写法
decision_date: 2026年9月8日
# 公示日期（该记录在官方渠道可见的日期），ISO 格式
published_on: 2026-09-24
# 公示期限，原样抄录
publicity_period: 五年
# 所属法域，MVP 阶段固定为 CN
jurisdiction: CN
# 涉及领域。归类是人工工作，未归类时留空数组是正常状态
domain: []
# 关联到本库的政策记录 id。填了它，这份罚单才具备校验义务清单的能力
related_policies: []
# 来源溯源：url 必须是**该当事人所在的那份公示文书**的地址，不是机构首页
source:
  url: https://www.pbc.gov.cn/zhengwugongkai/4081330/4081344/4081407/4081705/2026092418294123383/index.html
  site: pbc.gov.cn
  fetched_at: "2026-10-05T22:31:00+08:00"
  tier: primary
  http_status: 200
# 最近一次核验日期；尚未人工核验时留空
last_verified: null
# 核验方式：human = 已逐项人工核对；automated = 仅机器抄录
verified_by: automated
# 备注。automated 记录必须在这里说明抄录范围与核验方式
notes: 字段抄自人民银行行政处罚公示详情页表格原文，未逐项人工核对；official 公示不含处罚依据，故 legal_basis 留空
```

## 现状

目录当前为空。这不是遗漏，而是**有前置条件**：

`related_policies` 与 `domain` 的填写标准依赖「判定规则层」
（原子义务 + 判定条件 + 可靠性分级）尚未建立，在那之前录入的记录无法被有效关联，
只会在库里堆成一批孤立的罚单。抓取侧已经可用
（`finreg fetch --source pbc-administrative-penalties --force`），
第一批记录的录入等判定规则层就位后再做。

schema 见 [`schema/enforcement.schema.json`](../../schema/enforcement.schema.json)。
